# 你的整个 Git 历史，被一个 AI 工具悄悄打包上传了 564 次
### ——智谱 ZCode「偷传源码」事件始末

> 一个开发者只是清理了一下磁盘，却在自家电脑里翻出了一个 313 兆、打不开、删不掉的加密文件——里面装着他的整个项目，从第一次提交到今天。

## 一、一切从一个删不掉的文件开始

先把背景交代一句：智谱刚完成 **335 亿元融资**（2026 年），旗下 AI 编程客户端 **ZCode**（对标 Cursor 的 Coding Agent）用户数已突破 200 万、跻身国内前三。故事，就发生在这样一个风头正劲的产品上。

9 月 16 日，开发者 **ferstar** 在清理一台只有 256GB 存储的 MacBook Air 时，发现 ZCode 在用户目录下占了 700 多兆空间。对一个「没怎么用过」的工具来说，这不正常。

顺着目录翻下去，他在 `v2/checkpoints/` 里找到一份 **313MB 的加密文件**，旁边躺着一份明文状态文件，里面有三个字段：

- 这份快照来自他本地一个 **345MB 的商业项目**，被打包加密成 313MB 的「baseline 全量快照」；
- 上传尝试次数：**564 次，全部失败**，文件还留在本地的 pending 目录里等着第 565 次；
- 删除后约半小时，**一个新的 313MB 加密包又被生成**，计数器从 564 变成了 565——你删你的，它照传。

加密包本身解不开，但打包时留下的**明文文件清单**泄露了它的内容：本次打包覆盖 **42,411 个文件**。其中 Git 大文件缓存占 56.8%，Git 对象库（完整提交历史）占 29.6%，Git 日志占 0.2%——**.git 目录合计占整个包的 86.6%，当前源代码和文档只占约 13.4%**。

这意味着什么？写程序的人都明白：`.git` 不是「项目现在的样子」，而是**项目从出生到今天的完整档案**——每次提交、每个回滚、早期误传后删掉的密钥、没推上去的本地分支、内部 GitLab 域名、踩过的每个坑，全在里面。智谱要打包上传的，不是完成任务需要的那几段代码，而是**你的整个研发史**。

## 二、逆向拆包：上传链路被完全还原

ferstar 拆开了客户端的 `app.asar`，把整条链路还原了出来：

1. 客户端向 `zcode.z.ai` 申请快照上传凭证；
2. 服务器下发**阿里云 OSS 的签名、文件路径、大小限制，和一把 RSA 公钥**；
3. 客户端在本地把项目压成 tar.gz，用 **AES-256-CTR** 加密，再用服务器给的 **RSA 公钥**把密钥封装起来；
4. 加密包**绕过智谱自己的业务服务器，直传阿里云 OSS**，再由 OSS 回调智谱后台登记。

这不是一段没启用过的预留代码——ferstar 还发现，一份只有 538 个文件、加密后约 15KB 的**公开代码仓库快照，状态已经显示「服务端已接收」**。也就是说，上传是真实发生过的，不只是失败重试的那些。

更关键的是触发时机和操控权：

- **两个开关都是摆设**：设置里的「体验优化」只管数据是否授权用于训练，「仓库快照索引」只管服务端要不要给已上传的快照建索引——**两个都不阻止本地打包，也关不掉上传链路**；
- **触发频率惊人**：代码里有两个触发器，一个挂在**每次发送提示词之前**，一个挂在任务完成时的 `repo-wiki-update` 上。ferstar 的会话日志里，单次会话最多出现过 **62 次快照事件**；
- **钥匙在云端**：加密用的公钥由服务端下发，私钥只存在云端——**在你自己电脑上生成的加密包，连你自己和客户端本体都解不开**，只有智谱的服务器能还原全部代码；
- **历史目录豁免过滤**：文件筛选逻辑里，`.git` 历史目录的放行排在密钥过滤和 1MB 体积限制**之前**，导致针对 `pem`、`key` 这类密码文件的过滤对历史内容**完全失效**——历史上删掉的密钥照样会被打进包里；
- **隐私政策只字未提**：当时的 ZCode 隐私政策只写「收集你在**对话中提交**的文本、文件和代码」，整仓快照、Git 历史，一个字都没提。

## 三、是 bug，还是被持续迭代的功能？

9 月 16 日，也就是 ferstar 发文的两天前，ZCode v3.12.2 的更新日志里有一条：

> 「优化仓库快照上传的内存占用。」

社区很快把这条扒了出来——**一个工程团队，不会给「意外」专门优化内存。**「仓库快照上传」在内部显然是被持续迭代的正常功能，而不是某次失误带上去的残留代码。

智谱后来把原因归结为「代码库索引」功能：它原本用于在本地生成仓库索引，支撑会话检查点恢复、历史版本回退和 Repo Wiki；其中 Repo Wiki 在云端生成知识库页面时，可能触发仓库数据上传。

但这里有一个绕不过去的落差：**如果只是生成 Wiki / 支持回滚，为什么需要打包 LFS 缓存、已删除提交里的密钥、未推送分支的操作记录？**ZCode 官方文档自己都写明，生成说明文档时「不读取项目的历史修改记录，只按需读取经过筛选的代码上下文」——也就是说，这件事在技术上根本不需要完整 Git 历史。

## 四、智谱的回应：道歉、修复、承诺

9 月 18 日，ferstar 公开了完整调查，并在智谱的 GitHub 官方反馈仓库提了 Issue，质问三件事：**为什么一个检查点恢复功能需要完整 Git 历史？为什么解密私钥只由服务端持有、用户自己都打不开？为什么连关闭的开关都不给？**

当天 **17:44，智谱在 ZCode 用户群发布说明并致歉**，要点：

- 问题源于「代码库索引」功能，该功能**上线初期默认开启**，影响了部分用户；
- 触发上传的是云端生成 Repo Wiki 的环节，Wiki 生成后上传数据会**立即销毁、不会保存**；
- 问题**已经修复**；
- 后续将**开源 ZCode 代码库**、引入**第三方评估人员审查**并公开进展，同时为全体用户补偿一次周额度重置。

9 月 19 日，ZCode 发布 3.14.0，更新日志明确写着「修复仓库百科异常上传的问题」——这相当于变相承认了仓库数据确实被上传过。ferstar 对 3.14.0 做了复查，结论是旧版本里那条链路已经拆除：上传组件不再随客户端启动，`/api/v1/snapshot/upload-credential` 接口返回 404。

但问题没完。**「立即销毁」目前只是企业单方面的声明**——外部研究者能检查客户端是否发送数据，却进不了智谱的服务器验证文件什么时候删的、备份里有没有副本、私钥由谁保管、历史上传的数据有没有被真正清理。客户端更新只能阻止新的上传，**不能证明旧数据已经不存在**。而智谱承诺的开源和第三方审计，截至写稿日，开源仓库没有建起来，审计动作也没有公开。

## 五、升级：企业发函，数据出境疑云

9 月 19 日晚，**太原承明科技有限公司**向智谱公开发函，把这件事从技术争议拽进了法律与合规程序。

承明科技是一家做企业办公系统的中小公司。它通过独立取证发现，**8 月 28 日到 9 月 14 日期间，公司有超过 6 个工作区被 ZCode 上传到云端**，最大一个 391.94MB；还有一个项目被打包后因上传失败 32 次、侥幸留在本地。更何况——**在智谱公开致歉的当天凌晨，承明科技仍然检测到了上传行为**，这直接质疑了「问题已修复」的时间点。

函件里最关键的两点：

**第一，传走的远不是「代码片段」。** 承明科技指出，被打包的是结构完整的归档，包含：完整源代码和系统架构设计、完整的版本控制历史（含已删除的历史提交和引用日志）、**数据库口令、接口密钥、云服务凭证及证书、员工及终端用户的个人信息**，还有未公开的研发规划和商业计划——「远超《ZCode 隐私政策》载明的收集范围」。

**第二，数据可能出境了。** 承明科技发现，ZCode 客户端的全部网络请求都指向 `zcode.z.ai` 和 `cdn-zcode.z.ai` 两个域名，而 Z.AI 平台的隐私政策显示，其**缔约主体和个人数据控制者是注册在新加坡的 JINGSHENG HENGXING TECHNOLOGY PTE.LTD**——按智谱在港交所的招股书，这家公司是智谱 2023 年 11 月在新加坡注册的**间接全资子公司**。更微妙的是：英文版 ZCode 协议明确由这家新加坡主体提供服务和处理数据，**中文版协议却写着服务方是「北京智谱华章科技股份有限公司」**；中文版隐私政策还承诺「境内运营收集产生的个人信息存储于境内、不会跨境传输」。

两份协议，两个主体，跨境与否，没人说得清。承明科技在函件中提出 11 项要求，包括停止处理、删除数据及备份、披露处理记录、说明是否用于模型训练、提供删除证明，并限期 **10 月 10 日**前书面答复。截至写稿日，智谱尚未对函件公开回应。据报道，目前已有近 400 名开发者在多个维权群中抱团。

（9 月 20 日晚间，承明科技在抖音官号表示正在与智谱沟通，并将此前发布的函件内容临时隐藏。）

## 六、这不是智谱一家的事

如果说这起事件有什么「行业性」，那就是它和今年另外两起事故摆在一起，构成了一面镜子：

- **xAI 的 Grok Build（2026 年 7 月）**：安全研究者 cereblab 抓包发现，它会把用户的整个项目打包上传到谷歌云存储，**连用户明确告诉它「不要读」的文件、未经脱敏的密码都传走了**；用户在设置里关闭「改进模型」也不影响上传。事件曝光后 xAI 关闭了自动上传，马斯克表示将删除此前上传的数据。
- **Anthropic 的 Claude Code（2026 年 3 月）**：一次版本发布把约 60MB 源码映射文件误打进了安装包，随后社区又发现它每小时向官方服务器轮询远程配置、其中含可绕过用户权限提示的控制开关——Anthropic 工程师随后确认，这是一次**功能实验**。

三家的共同点是什么？**AI 编程 Agent 的权限已经接近开发者本人了**——它能遍历文件、读代码、执行命令、改整个项目——而整个行业的数据治理，还停留在「默认勾选」和一份模糊的隐私协议阶段。谁是第一个撞上这条红线的？**三起事故被发现，都是偶然**：一次靠配置失误泄露、一次靠安全研究者主动抓包、一次靠博主对磁盘空间不对劲的警觉——没有一起来自厂商自查、行业审计或监管巡查。

智谱这一单和另外两家的差别在于纵深：Grok Build 的问题主要是没尊重文件排除设置，Claude Code 传的是行为元数据，而 **ZCode 把「整仓打包 + 完整 Git 历史 + 私钥云端独占 + 开关失效 + 删了重建」叠在了一起**。这也让它成了国内第一个被公开完整还原整个上传链路的 AI 编程工具案例。

## 七、结语：你使用模型，不等于你同意成为模型的数据

写到这里，把确认的和没确认的分开：

**已经确认的**：登录状态下 ZCode 会打包加密整个工作区、含完整 Git 历史上传云端；开关关不掉；解密密钥只在云端；触发频繁；隐私政策未披露；智谱承认该功能默认开启、宣布修复并承诺开源与审计。

**还没有答案的**：已上传的数据是否真的「立即销毁」？是否曾进入训练数据池、评测集或人工分析流程？覆盖了多少用户、多少企业仓库？有没有跨境？——**这些问题，到目前为止没有任何外部机构能独立验证**。你唯一能收到的是客户端不再上传，而不是「你的数据已经不在别人手里」。

熟悉行业的人都知道，编码类交互是当下公认的高质量训练数据：用户提出任务、模型生成代码、开发者再修改接受——这中间包含着比公开互联网数据高得多的信息密度。数据要拿，可以；问题从来不是「模型厂商想要数据」，而是**它做了，却没告诉你，也不给你选择**。

这起事件真正该被记住的，不是某一家公司的安全能力，而是整个行业是否愿意承认一条最基本的边界：

> **用户使用模型，不代表用户同意成为模型的训练数据。**

对个人开发者，最后留几句能落地的建议：企业项目别把真密钥、生产配置放进本地 Git 历史（该轮换的轮换）；先读清楚代码工具的隐私政策再登录使用；从今天起留意一下你电脑上那些「常用开发工具」的磁盘占用和出站流量——**下一次「偷东西」被抓到现行，可能又是一个清理磁盘的开发者。**
